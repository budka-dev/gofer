# Модель безопасности

Что попадает в индекс, что выходит наружу, где границы изоляции и где их нет. Этот документ — для тех, кто хочет понять риски до интеграции.

**Главное:** gofer спроектирован как **локальный** инструмент в доверенной среде разработки. Он не задумывался как хардненный сервис для многопользовательской/публичной среды. Если планируется такое использование — нужны дополнительные слои защиты, не входящие в gofer.

gofer — **read-only** инструмент: он не модифицирует файлы, не выполняет код проекта, не поднимает внешних процессов кроме HTTP-эмбеддера и загрузки wasm-грамматик.

## Что и куда уходит

### Локально на диск

- `<project>/.gofer/data/index.sqlite` — все метаданные, символы, ссылки, фрагменты содержимого (для FTS), кеш эмбеддингов.
- `<project>/.gofer/data/lance/` — векторы эмбеддингов всех проиндексированных чанков. По векторам можно частично реконструировать исходный текст (теоретически — с дорогой optimization-атакой; на практике маловероятно для случайного злоумышленника, но **уязвимо для целевой атаки** при доступе к диску).
- `~/.gofer/registry.sqlite` — список зарегистрированных проектов с путями.
- `~/.gofer/daemon.log` / `daemon.err` — логи. Могут содержать пути файлов, фрагменты сообщений об ошибках, но **не** содержимое файлов целиком.
- `~/.gofer/langs/<lang>/` — скачанные wasm-грамматики (публичный код, не sensitive).

### По сети

- **Внешний эмбеддер.** Каждый чанк файла отправляется POST-запросом на `[embedding].external_url`. Это содержимое **уходит за пределы машины**, если эмбеддер крутится на удалённом сервере. См. ниже про эмбеддер attack surface.
- **lang-hub.** При `gofer install-lang <name>` или авто-скачивании грамматики gofer обращается к `https://raw.githubusercontent.com/budka-dev/lang-hub/...` и `https://github.com/budka-dev/lang-hub/releases/...`. Только HTTPS, никакой авторизации.
- **Метрики Prometheus.** Слушает `127.0.0.1:9091` — только localhost, не доступно извне.

### По IPC

- `~/.gofer/daemon.sock` — Unix socket. Доступ ограничен правами файла (см. ниже).

## Что **не** уходит наружу автоматически

- Никаких telemetry-каналов. gofer не шлёт usage stats никуда.
- Никаких background-обновлений бинаря или конфига.
- Никаких CI-/cloud-интеграций без явной настройки.
- `git` команды gofer не запускает в фоне (только по запросу через `git_*` инструменты).

## Границы и риски

### Что индексируется

**Всё, что не отфильтровано:**

1. `.gitignore` файлы проекта (через crate `ignore`).
2. Захардкоженные исключения: `.git`, `.gofer`, `.qoder`, `*.lock` (`watcher.rs::build_gitignore`).
3. Пользовательские `[indexer].ignore` из `.gofer/config.toml`.
4. Файлы >2 МБ скипаются (`MAX_FILE_SIZE_BYTES`).
5. Файлы с расширениями, не известными `SupportedLanguage`, игнорируются.

**Чего gofer не делает:**

- Не сканирует регулярки на секреты.
- Не маскирует переменные окружения.
- Не отличает «приватные» файлы от «публичных» иначе чем по этим правилам.

**Практика:** добавь в `.gitignore` или `[indexer].ignore`:

```
.env
.env.*
secrets/
credentials/
*.pem
*.key
id_rsa*
*.p12
```

Если файлы уже в индексе — снеси `.gofer/data/` и переиндексируй.

### Что попадает в эмбеддер

Каждый текстовый чанк → POST на `external_url`. Если эмбеддер — третий стороны (OpenAI, HuggingFace TEI на чужом сервере), это утечка кода через сеть.

**Митигейшены:**

1. **Локальный эмбеддер.** Самый чистый вариант: TEI/FastAPI на localhost или VPN-only хосте.
2. **Self-hosted.** Свой TEI на корпоративном сервере.
3. **API-ключ.** Если эмбеддер требует auth — `[embedding].external_api_key`, gofer добавит `x-api-key`.
4. **TLS.** `reqwest` поддерживает `https://`. Без верификации сертификата (флага `danger_accept_invalid_certs`) gofer не работает.

Никакого encryption-at-rest для отправки нет; это задача транспорта.

### IPC доступ (Unix socket)

Сокет `~/.gofer/daemon.sock` создаётся с правами по умолчанию (`umask` пользователя — обычно `0600` для домашнего каталога). Это значит:

- Тот же пользователь имеет полный RW-доступ.
- На большинстве систем root тоже (как обычно).
- Других пользователей нет (если umask стандартный).

**Кто угодно с RW к сокету = полный контроль над демоном:** может слать любые `tools/call`, читать любой файл проекта через `read_file`, инициировать переиндексацию. Если на машине есть другие пользователи и общий доступ к `~/.gofer/` — это уязвимость.

**Митигейшены:**

- Не давай другим пользователям доступ к `~/.gofer/`.
- На shared-системах — отдельные `$HOME` per user, как обычно.
- Можно патчить путь сокета под per-project конфигурацию (сейчас он глобальный).

## Аудит

Каждый MCP-вызов журналируется в `audit_log` (миграция `011_audit_log.sql`): имя инструмента, аргументы (как JSON), latency, timestamp. Запись делается через `SqliteStorage::log_tool_call`.

Хочешь посмотреть кто что вызывал:

```sql
SELECT timestamp, tool_name, args, latency_ms
FROM audit_log
ORDER BY timestamp DESC
LIMIT 100;
```

## Чек-лист безопасной интеграции

Если используешь gofer в команде / на не полностью доверенной машине:

- [ ] Проверь `.gitignore` и `[indexer].ignore` — секретов не должно остаться в индексе.
- [ ] Эмбеддер локальный или в твоей сети (не сторонний публичный сервис, если не хочешь делиться кодом).
- [ ] HTTPS на эмбеддере, если он за пределами `127.0.0.1`.
- [ ] `~/.gofer/` доступен только тебе (`ls -la ~/.gofer/` → owner-only).
- [ ] При работе с чужим эмбеддером с auth — `external_api_key` через переменную окружения, не в commited config.

## Что **не** считается уязвимостью

- gofer индексирует `.env` если он не в `.gitignore` — обязанность пользователя.
- `tools/call` шлёт что-то на эмбеддер — обязанность пользователя сконфигурировать локальный эмбеддер.

## Куда сообщать о проблеме

Если нашёл реальную дыру (например, обход path-jailing с `..`, утечку через лог) — issue/email на репозиторий. Public disclosure лучше координировать с автором.
