# Benchmarks: экономия токенов и точность

Сводная таблица замеров из `tests/*_comparison.md`. Полные отчёты с методологией и итерациями — в [tests/README.md](../tests/README.md). Здесь — выжимка: **сколько gofer экономит и где он лучше/хуже native**.

## Зачем

Перед тем как подключать gofer как MCP-сервер, обычно хочется ответ на «а это вообще даёт что-то?». Ниже — реальные цифры по типовым сценариям.

Замеры проведены на pet-проекте gofer'а самого по себе (~32K LOC Rust). Цифры зависят от размера файлов и характера задачи — используй их для понимания порядка, не как SLA.

## Сводка

| Инструмент | vs Native | Точность | Экономия токенов | Скорость |
|---|---|---|---|---|
| `skeleton` | vs `Read` (полное чтение) | 100% / 69% | **76%** (в 2.2× меньше) | Read на 24% быстрее (63 vs 83 мс) |
| `read_function_context` | vs `grep`/`sed` | 100% / 51% | оптимально (только функция) | Native в 2.6× быстрее (25 vs 65 мс) |
| `read_types_only` | vs `grep` | 100% / 60% | 40–70% экономия | Native в 3.5× быстрее (14 vs 49 мс) |
| `context_bundle skeleton_deps_only` | vs ручное собирание | 100% / низкая | **~40% экономия** на больших файлах | сопоставимо |
| `batch_operations` | vs последовательные вызовы | равны | ~5–10% за счёт unified output | **в 3–5× быстрее** на параллели |
| `clipboard_*` (CAS-буфер) | vs повторная передача | 100% (хеш-точность) | **70–90% экономия** при N=3+ вставок | сопоставимо |

Главное: gofer почти **всегда точнее** и **экономнее по токенам**, но **медленнее на одну операцию** (overhead JSON-RPC + парсинга). Эти задержки компенсируются за счёт `batch_operations` и того, что одна gofer-операция эквивалентна 2–20 native-вызовам.

## skeleton vs read_file

Конкретные цифры из `tests/03_skeleton_vs_read_comparison.md`:

| Файл | Строк | Skeleton tokens | Read tokens | Экономия |
|---|---|---|---|---|
| error_recovery.rs | 113 | 350 | 1100 | **68%** |
| cache.rs | 515 | 1450 | 4800 | **70%** |
| sqlite.rs | 2261 | 6200 | 20000 | **69%** |
| parser/core.rs | 2133 | 3200 | 21000 | **85%** |
| **Среднее** | | **2800** | **11725** | **76%** |

Дополнительно: точность `Read` падает до 5% на файлах >2000 строк (clamp на 2000 в Claude Code).

**Когда использовать:** для **любого** чтения файла >150 строк, если детали реализации не критичны.

## read_function_context vs grep/sed

Из `tests/15_read_function_context_comparison.md`:

| Случай | Gofer точность | Native точность (grep+sed) |
|---|---|---|
| Простая функция | 100% | 40% (множественные совпадения) |
| Async функция | 100% | 60% (ручной поиск конца) |
| Большая функция | 100% | 50% (ошибки в границах) |
| Match-выражение | 100% | 65% (лишние строки в `}`) |
| Несуществующая | 100% | 50% (молчаливый fail) |

**Среднее: 100% vs 51%.** Точность важнее скорости в этом сценарии: ассистент не любит читать «функцию + половину следующей».

**Когда использовать:** когда нужна одна функция (и её зависимости через `include_types`), не сам файл.

## read_types_only vs grep

Из `tests/16_read_types_only_comparison.md`:

| Случай | Gofer | Native |
|---|---|---|
| Несколько структур | 100% | 80% |
| Enum | 100% | 60% |
| **31 структура в файле** | **100%** | **10%** (только 3 из 31) |
| Приватные | 100% | 50% |
| Несуществующая | 100% | 100% |

**Среднее: 100% vs 60%.** На больших файлах с множеством типов native-grep массово промахивается из-за regex-ограничений.

**Когда использовать:** при анализе модели данных модуля, перед написанием нового handler'а, при review API.

## context_bundle skeleton_deps_only

Из `tests/13_context_bundle_comparison.md`. Сценарий: файл на 1170 строк с 10 import-зависимостями.

| Подход | Размер | Tokens |
|---|---|---|
| Native: только основной файл | 1170 строк | ~9000 |
| Native: основной + полные deps | 1170 + 10×1000 | **~19,000** |
| Gofer `context_bundle skeleton_deps_only=true` | 1170 + 10×250 | **~11,500** |

**Экономия 40% (~7500 tokens)** против полного собирания. Точнее: ассистент получает полный код целевого файла + скелеты зависимостей с типами, импортами, сигнатурами — для big-picture этого достаточно.

**Когда использовать:** когда работаешь над файлом и нужен контекст его зависимостей.

## batch_operations

Из `tests/07_batch_operations_comparison.md`. Три типовых сценария:

| Сценарий | Native (3 запроса) | Gofer batch | Экономия latency |
|---|---|---|---|
| Read 3 файла | ~7000 tokens | ~6100 tokens | **3× меньше latency** (параллель) |
| File + symbols + search | ~13,000 tokens | ~11,500 tokens | **3–4× меньше latency** |
| Read 10 файлов | ~44,000 tokens | ~42,000 tokens | **5× меньше latency** |
| Ошибочные запросы | ~1400 tokens | ~1200 tokens | сравнимо |

Главный выигрыш — **latency**, не токены. При сетевом overhead в 30–50 мс на запрос batch экономит сотни миллисекунд.

**Когда использовать:** всегда, когда независимые операции можно сгруппировать. Особенно: предварительный sweep перед началом задачи.

## CAS-буфер (clipboard_*)

Из `tests/21_hash_buffers_comparison.md`. Сценарий: блок кода нужно вставить N раз в разных файлах.

| N вставок | Native (повторная передача) | Gofer (один hash) | Экономия |
|---|---|---|---|
| 1 | равно | равно | 0% |
| 3 | 3×размер_блока | 1×размер + 3 hash-ссылки | **~70%** |
| 5 | 5×размер | 1×размер + 5 ссылок | **~85%** |
| 10 | 10×размер | 1×размер + 10 ссылок | **~90%** |

Дополнительный плюс: **точность 100%** — сервер раскрывает hash обратно в исходный текст, ассистент не галлюцинирует при копировании.

**Когда использовать:** при рефакторинге (переместить блок), при шаблонной вставке в N мест, при «вырезать и вставить позже».

## Где gofer **не** даёт выигрыша

Честно про сценарии, где gofer не нужен:

- **Чтение маленького файла (<100 строк) целиком.** Overhead JSON-RPC ≥ экономии токенов. Использовать `read_file` тут OK, но native `cat` чуть быстрее.
- **Поиск точной строки.** Если знаешь точный pattern — ripgrep быстрее `search` (BM25 и эмбеддер не нужны).
- **Глобальный rename одной переменной.** `lsp_rename` точнее, но overhead подключения LSP может перекрыть выигрыш. На очень крупных проектах rename через LSP всё равно надёжнее.
- **Когда индекс устарел.** Если только что был большой `git pull` и watcher не успел догнать — `search` отдаст старое. Сделай `get_index_status` сначала.

## Методология

Все замеры по [тестовой методологии](../tests/00_methodology.md):

1. **Функциональность** — работает ли вообще.
2. **Точность (0–100%)** — насколько точно отвечает.
3. **Эффективность** — токены и операции на ответ.
4. **Скорость** — wall-time от запроса до ответа.

Замеры делались итеративно по 5 случаев на инструмент, среднее в таблицах выше.

## Воспроизвести самому

Если хочешь замерить на своём проекте:

```bash
# Поднять gofer
gofer up && gofer init && gofer start

# Замерить через time
time gofer mcp <<< '{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"skeleton","arguments":{"file":"<file>"}}}'

# Получить число токенов
gofer mcp <<< '...' | wc -c  # делить на ~4 (грубая эвристика)
```

Точные замеры — через timing-обёртку MCP-клиента или Prometheus метрики (`gofer_avg_query_latency_us`).

## Ограничения замеров

- Все цифры — на pet-проекте gofer'а самого. На крупных монорепо латентность будет выше за счёт большего ANN-индекса.
- Эмбеддер локальный CPU. На GPU-эмбеддере latency `search` падает в 3–5×.
- Метрики «токенов» — оценка по эвристике `chars/4`. Реальное число зависит от tokenizer'а конкретной LLM.

## TL;DR

Если выбирать одну фразу: **используй gofer для всего, что больше одной маленькой read-операции, и обязательно — для семантического поиска и context-bundle сценариев.**
