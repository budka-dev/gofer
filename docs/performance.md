# Производительность и эксплуатация

Что ожидать по ресурсам, какие сценарии быстрые, какие медленные, и куда смотреть, когда упёрся.

Цифры в этом документе — порядковые: они зависят от железа, размера проекта и эмбеддера. Используй их для ориентира, не как SLA.

## Что потребляет ресурсы

### RAM

- **Демон в покое (без активных проектов):** ~50–80 МБ. В основном — tokio runtime, sqlx pool, реестр проектов.
- **Один активный проект, 10K LOC, ~150 файлов:** +150–300 МБ. Львиная доля — LanceDB index в памяти и `scoring_index` (mmap, считается в RSS).
- **Один активный проект, 100K LOC, ~1500 файлов:** +500 МБ–1 ГБ.
- **Несколько активных проектов:** примерно аддитивно.

`scoring_index.rs` — mmap, фактически в RAM сидит только горячая часть. На больших проектах размер файла на диске может быть сотни МБ, но RSS прирастает только при активном скоринге.

jemalloc по умолчанию отдаёт зарезервированную, но не использованную память не сразу. RSS в `top` обычно выше реального usage. Это **не утечка**.

### Диск (`.gofer/data/`)

| Что | Примерный размер | Заметки |
|---|---|---|
| `index.sqlite` | ~5–20 МБ на 10K LOC | Метаданные, символы, refs, кеш чанков. Растёт линейно с числом файлов. |
| `lance/` | ~50–200 МБ на 10K LOC при dim=768 | Векторы доминируют. Прямо пропорционально dimensions × num_chunks. |
| `scoring_index.rkyv` | ~1–5 МБ на 1K файлов | Очень компактный, rkyv сильно жмёт. |
| WAL | переменный | `gofer down` сворачивает. |

Оценка: при `dimensions = 768` каждый чанк это `768 × 4 = 3 КБ` вектор + ~1 КБ метаданных. 10K чанков ≈ 40 МБ Lance. На 100K-LOC Rust-проект обычно выходит ~500 МБ суммарно.

### CPU

- **Полная индексация 10K LOC:** ~10–60 с, доминирует HTTP-эмбеддер. CPU-нагрузка на gofer — низкая (parser worker'ы пакуют батчи быстро, embedder-стейдж ждёт сеть).
- **Инкрементальная индексация одного файла:** 100–500 мс. Большая часть — пинг эмбеддера и SQL запись.
- **Search-запрос:** 20–100 мс на горячем кеше, до 500 мс при холодном.
- **`get_symbols`/`grep`:** обычно <50 мс.

## Что ограничивает throughput

В порядке убывания значимости:

1. **HTTP-эмбеддер.** Если он на CPU и считает медленно — pipeline стоит. Поднимай размер батча на сервере или модель поменьше.
2. **Диск.** SQLite с WAL и LanceDB вместе дают неприятный паттерн рандомных IOPS. На HDD индексация в 5–10 раз медленнее, чем на SSD.
3. **Tokio worker threads.** По умолчанию `max(num_cpus/2, 4)`. На 4-ядерной машине это 4 потока — узким местом редко бывает.
4. **CPU при tree-sitter parse.** Заметно только на гигантских монолитных файлах (>10K строк). Файлы >2 МБ скипаются (`MAX_FILE_SIZE_BYTES`).

## Capacity planning

Грубые ориентиры для оператора:

| Размер проекта | LOC | Файлов | RAM | Disk | Время полной индексации* |
|---|---|---|---|---|---|
| Маленький | <5K | <100 | ~100 МБ | <50 МБ | <10 с |
| Средний | 10K–50K | 500–2000 | 300 МБ – 1 ГБ | 100 МБ – 500 МБ | 30 с – 3 мин |
| Большой | 100K+ | 3000+ | 1–4 ГБ | 500 МБ – 2 ГБ | 2–10 мин |
| Монорепо | 500K+ | 10K+ | 4–10 ГБ | 2–8 ГБ | 10–60 мин |

\* при локальном эмбеддере на CPU. На GPU-эмбеддере умножай скорость на 5–20×.

## Что тюнить, когда медленно

### Эмбеддер — основной рычаг

- Поднять `pool_size` в `[embedding]` (до 8).
- Поднять `batch_size` (если сервер тянет).
- Перейти на GPU-эмбеддер (TEI с CUDA, sentence-transformers + torch.cuda).
- Уменьшить `dimensions` (требует пересчёт индекса).

См. [embedder.md](embedder.md).

### SQLite

WAL включён по умолчанию. На больших проектах может помочь:

```sql
PRAGMA cache_size = -65536;     -- 64 МБ
PRAGMA synchronous = NORMAL;    -- меньше fsync
PRAGMA mmap_size = 268435456;   -- 256 МБ
```

Сейчас эти `PRAGMA` не выставляются — патч в `SqliteStorage::open` решит.

### LanceDB

- `lance.compact()` вызывается в конце pipeline (`pipeline.rs:236`), но при частых мелких инкрементах фрагменты копятся. Раз в N часов помогает запустить `gofer reindex` или ручной compact.
- Размерность вектора прямо пропорционально влияет на размер хранилища и скорость search. 384/768 — нормальный диапазон, >1024 уже жирно.

### Watcher

- При >10K файлов в проекте дебаунс 500 мс может оказаться мал — события сливаются, но всё равно много обновлений в секунду.
- На Linux подними `fs.inotify.max_user_watches` до 524288 (см. [troubleshooting.md](troubleshooting.md#watcher-не-видит-изменения)).

## Профилирование

### Метрики Prometheus

```bash
curl 127.0.0.1:9091/metrics
```

Что смотреть:

- `gofer_queries_served_total` — счётчик запросов.
- `gofer_avg_query_latency_us` — средняя латентность поиска. Если ползёт вверх — посмотри cache hit-rate.
- `gofer_total_files_indexed` / `gofer_total_chunks_embedded` — кумулятивные счётчики.
- `gofer_last_sync_duration_ms` — длина последней полной индексации.

### Tool-метрики

```
get_cache_stats     -> hit-rate серверного LRU
get_query_stats     -> распределение latency по запросам
get_index_status    -> completeness индекса
```

### `gofer status` + логи

```bash
gofer status
gofer logs -n 200
```

В логах ищи `Pipeline:` для стейджей индексации, `Embedder` для сетевых вызовов, `Circuit breaker` для отказов.

## Масштабирование

gofer задуман как **локальный** ассистентский сервис: один демон на машину, обслуживающий любое количество MCP-клиентов. Горизонтальное масштабирование (несколько демонов, шардинг, реплики) не реализовано и не планируется в текущей итерации.

Возможные конфигурации:

- **Один эмбеддер на команду.** Несколько разработчиков указывают одинаковый `[embedding].external_url`, который смотрит на shared TEI-сервис. Кеш чанков остаётся per-проект (в локальной SQLite).
- **GPU-эмбеддер в кластере.** Полезно для крупных монорепо. Доступ через VPN или K8s ingress.
- **Отдельный демон на проект.** Технически возможен — нужно патчить `gofer_home()` под env-переменную, сейчас он жёстко `~/.gofer/`.

## Memory leaks?

gofer написан на Rust, явных утечек не должно быть. Но:

- jemalloc не возвращает RSS системе оперативно — RSS «застревает» на пике после крупной операции.
- LSP-клиенты держат живые stdio-pipes; если LSP-процесс сошёл с ума, gofer не убивает его автоматически.

Если что-то заметно растёт без причины — `gofer down && gofer up` сбросит всё чисто. Если нужно отследить — поднимай с `JEMALLOC_CONF=prof:true,prof_active:true,lg_prof_sample:19` и анализируй `jeprof`.

## Известные узкие места

- **Re-rank сейчас не реализован**, хотя `rerank=true` ожидается в API (`search`). Влияет на качество поиска, но не на скорость.
- **Generic LSP** запускается при первом обращении к файлу и живёт до shutdown'а. Если LSP не используется — это просто RAM, занятая впустую.
- **`scoring_index` rebuild** случается после полного sync целиком; для очень больших проектов это пик RAM.
